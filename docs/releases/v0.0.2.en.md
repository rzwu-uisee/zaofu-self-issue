## v0.0.2

v0.0.2 is a reliability and real-delivery closure release. It does not expand
the Kernel's autonomy boundary. It focuses on defects exposed by a real Codex
product E2E across Channels, Workflows, task handoffs, recovery, and terminal
goal decisions.

```text
ambiguous request
  -> structured clarification by the Kanban Agent
  -> multi-role Channel discussion + Owner decisions
  -> Owner-confirmed PRD
  -> Task + Plan/Approve Workflow
  -> task map / source / briefing / candidate
  -> independent verify / recovery / goal closure
```

The central improvement is continuity: the original request, Owner decisions,
task contract, and current authoritative evidence remain intact across pages,
agents, attempts, and recovery cycles.

## Release Highlights

### 1. Channel to Owner-Confirmed PRD

- Channel Groups can materialize a role-based discussion while preserving role
  bindings, skills, history, and targeted routing.
- Owner questions use stable question IDs and support batched answers, Back,
  revisions, and refresh recovery without silently dropping later questions.
- Discussion graphs, question graphs, role findings, and consensus use durable
  references.
- A late Owner decision creates a new PRD revision instead of overwriting an
  already confirmed revision.
- Task and Workflow delivery admission requires required-role consensus, Owner
  decisions, and canonical PRD provenance.
- Channel ingress and workflow routing enforce single ownership to reduce
  duplicate reactors, replies, and workflow ignition races.

### 2. One Durable Ask User Question Model

Kanban Agent, Channel, and Workflow questions now follow the same persistence
rules:

- Single-choice cards, Customize/Other, Back, keyboard control, and multi-batch
  submission are supported.
- Each question round binds request identity, question IDs, revision, and
  digest.
- Workflow clarification uses compare-and-swap. A stale revision is rejected
  instead of overwriting a newer question set.
- Pending questions and submitted answers survive page changes, refreshes, and
  Web restarts.
- When a provider does not support its native Ask API, ZaoFu preserves that
  capability boundary and does not reinterpret an ordinary tool result as an
  approval.

### 3. Faithful Plan, Task, and Worker Inputs

- Structured child call results, ports, and source refs survive plan synthesis.
- Task maps, source indexes, task docs, and briefings preserve canonical PRD
  and acceptance provenance.
- Writer briefings consistently begin with `Active task: <task_id>`, allowing
  recovery tooling to verify task identity fail-closed.
- A dispatched TaskContract revision no longer drifts because a projection or
  retry changes later.
- A lost Reader dispatch can be redriven for the current attempt, and a causal
  gap plan settles the prior failure checkpoint when complete.
- Terminal Workflow proposal replay is rejected, and Kanban Plan actions are
  available only when their inputs are ready.

### 4. Hardened Long-Horizon Recovery and Handoffs

v0.0.2 tightens Writer, Reader, fanout, semantic replan, and task-ref repair:

- Provider turns carry a launch-generation fence so an old process cannot
  impersonate the current launch.
- Writer handoff, session replacement, and fanout synthesis recovery preserve
  the current continuation baseline.
- Retry checkpoints, gap replacements, task refs, dispatches, and fanout
  lineage use consistent identities.
- Stale fanout recycling, superseded stalls, and terminal Channel failures do
  not produce unbounded duplicate delivery.
- Semantic replan prefers structured output and preserves flow, source,
  replacement, and handoff context.
- Contract blockers and equivalent retry/rework budgets are scoped to the
  current operation instead of being contaminated by another Run.
- Unknown human blocking scopes fail closed. Only an explicit side scope is
  non-blocking.
- An ordinary `worker.context.warning` remains an observation in the Kernel
  lifecycle and cannot create a second recovery state machine.

### 5. Current-Authority Verification, Goals, and Dossiers

- Verification discovery binds to the current verification identity instead
  of consuming historical rescans.
- Candidate lineage, task-map verification paths, and global rescan results
  require current authority.
- Run completion profiles include only human, verify, and terminal signals
  belonging to the current Run.
- Goal completion accepts only verifiable evidence for the current goal
  authority.
- Goal Dossiers and completion use the same current authority and do not
  converge on equivalent but stale historical claims.
- Agents still cannot self-declare terminal success. Missing independent human
  or verification evidence keeps a Run active or blocked.

### 6. Web, Loop, and Diagnostics

- Channel question cards, controlled actions, and Workflow clarification use a
  consistent interaction model.
- Channel, Task, Workflow, Trace, and Loop references survive refresh and
  cross-page navigation.
- Loop surfaces recovery, blocking, and replan signals while remaining a
  projection rather than canonical state.
- Web event-cache tests are isolated from the real workspace.
- Pytest isolates `ZF_WORKSPACE_HOME`, preventing each test Web app from
  prewarming a large real project registry. `test_web_server.py` dropped from
  roughly an hour without completion to about 25 seconds.

### 7. Real Codex Product E2E

This release exercised an isolated new project through the following real
path:

1. Initialize and register a Project from the Web interface.
2. Let the Kanban Agent inspect available templates and workflow routes without
   receiving internal IDs from the operator.
3. Run five real Codex Channel roles and close 11 Owner questions in 3+3+3+2
   batches.
4. Create a canonical Task with exact Owner-confirmed PRD r2 provenance.
5. Run a Plan/Approve Workflow that produces scans, a corrected plan, task map,
   source index, task docs, briefings, plan ports, and a candidate.
6. Pass 17 candidate product tests, the build, and 11/11 Docker Playwright
   tests.
7. Verify desktop and mobile Dashboard pages without horizontal overflow,
   permanent loading, page errors, or API 4xx/5xx responses.

The E2E correctly remained `BLOCKED` because the PRD required independent
human WCAG 2.2 AA evidence. The agent refused to impersonate a human reviewer,
and Run Manager preserved the release blocker. That is expected fail-closed
behavior, not a fabricated green terminal state.

## Upgrade Notes

### 1. Refresh Dependencies and Check the Version

```bash
uv sync --extra dev --extra web --extra stream-json
npm --prefix web ci
uv run zf --version
```

Expected output:

```text
zf 0.0.2
```

### 2. Validate Project Configuration

```bash
uv run zf validate --cold-start
uv run zf start --dry-run --no-watch
```

v0.0.2 remains a Developer Preview. Archive the configured state directory
before upgrading a long-running project, render and inspect the Controller
again, and validate current task, attempt, workflow, candidate, and goal
authority in isolated state. Do not assume experimental runtime state can be
resumed across versions without validation.

### 3. Start the Dashboard

```bash
tools/start-webkanban.sh --host 127.0.0.1 --port 8001
```

Bind to `0.0.0.0` only on an explicitly trusted network and enable a Web action
token.

## Known Limitations

1. **Human WCAG release gate:** a complete product Run still requires the
   specified independent reviewer evidence. An agent will not sign it on a
   human's behalf.
2. **Browser runner contract:** a target project's Playwright gate should bind
   an explicit Docker runner or declare host installation requirements.
3. **Web residuals:** the strict browser probe records one low-risk favicon
   404, and Observability remains the slowest measured page.
4. **Exactly-once release proof:** the real E2E was a repair continuation. A
   clean-HEAD release run with no ZaoFu code changes is still required.
5. **OpenCode:** the extensible provider SPI and native OpenCode session are
   designs in this release, not a shipped provider implementation.
6. **Compatibility:** Python APIs, Web APIs, event schemas, Controller
   profiles, and parts of the CLI may still change incompatibly before 1.0.

- 7 flow smoke tests;
- 17/17 real candidate product tests, the build, and 11/11 Docker Playwright
  tests.

Before creating the `v0.0.2` tag, rerun from the final version commit:

```bash
python scripts/dev-verify.py run --base dev
npm --prefix web run build
```

Also complete at least one clean real-provider release E2E without changing
ZaoFu code during the run. The release tag must point to that verified commit;
generating these release notes does not itself create a release tag.

## Summary

v0.0.2 does not hide delivery risk behind more autonomy. It makes ZaoFu more
reliable at preserving requirements, questions, tasks, attempts, candidates,
verification, and goal authority during real multi-agent product development,
and it remains blocked when the required evidence does not exist.
