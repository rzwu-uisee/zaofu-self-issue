## v0.0.2 版本

v0.0.2 是 v0.0.1 之后的稳定性与真实交付闭环版本。它没有扩大 Kernel 的自治边界，
而是集中修复真实 Codex 产品 E2E 暴露的 Channel、Workflow、任务交接、恢复和终态
判定问题。

```text
模糊需求
  -> Kanban Agent 结构化澄清
  -> Channel 多角色讨论 + Owner decision
  -> Owner-confirmed PRD
  -> Task + Plan/Approve Workflow
  -> task map / source / briefing / candidate
  -> independent verify / recovery / goal closure
```

本版本的核心变化是：同一产品需求在跨页面、跨 Agent、跨 attempt 和跨恢复周期流转时，
仍然保留原始问题、Owner 决策、任务合同、当前权威证据和确定性状态边界。

## 发布亮点

### 1. Channel 到 Owner-confirmed PRD 的产品闭环

- Channel Group 可以根据需求创建多角色讨论，并保留角色、skills、历史和定向路由。
- Owner 问题使用稳定 question id，可以分批回答、返回修改、刷新后继续，不再静默丢失
  第 4 个及后续问题。
- discussion graph、question graph、角色结论和 consensus 使用持久化引用保存。
- late Owner decision 会生成新的 PRD revision，而不是覆盖已经确认的旧内容。
- 只有满足 required-role consensus、Owner decision 与 canonical PRD provenance 的结果，
  才能进入 Task 和 Workflow delivery admission。
- Channel ingress 与 workflow routing 采用单 owner 约束，降低重复 reactor、重复回复和
  竞争点火。

### 2. 三类统一 Ask User Question

Kanban Agent、Channel 和 Workflow 现在共享一套持久化交互原则：

- 支持单选、卡片选项、Customize/Other、Back、键盘操作和多题分批提交。
- 每轮问题绑定 request、question id、revision 与 digest。
- Workflow clarification 使用 compare-and-swap；旧 revision 的提交返回冲突，而不是
  覆盖新问题。
- 页面刷新、跨页和 Web 重启后仍可恢复未完成问题与已提交答案。
- Provider 不支持原生 Ask API 时保持显式能力边界，不把普通 tool result 误判为授权。

### 3. Plan、Task 与 Agent 输入保真

- Plan child 的结构化 call result、ports 和 source refs 会传递到 plan synthesis。
- task map、source index、task docs 和 briefing 保留 canonical PRD 与 acceptance provenance。
- Writer briefing 首行稳定绑定 `Active task: <task_id>`，恢复脚本可以 fail-closed 地核对
  当前任务身份。
- 已派发 TaskContract 的 revision 不再因后续 projection 或重试发生漂移。
- Reader dispatch 丢失时可以基于当前 attempt redrive；旧 failure checkpoint 在 causal
  gap plan 完成后会被正确结算。
- terminal Workflow proposal 重放会被拒绝，Kanban 的 Plan action 只在输入满足 readiness
  时开放。

### 4. Long-horizon 恢复与接力加固

v0.0.2 系统性收紧了 Writer、Reader、fanout、semantic replan 和 task-ref repair：

- provider turn 增加 launch generation fence，旧进程不能冒充当前启动代次。
- Writer handoff、session replacement 和 fanout synth 恢复保留当前 continuation baseline。
- retry checkpoint、gap replacement、task ref、dispatch 和 fanout lineage 使用一致身份。
- stale fanout recycle、superseded stall 和 terminal channel failure 不会无界重复投递。
- semantic replan 优先消费结构化输出，并保留 flow、source、replacement 和 handoff context。
- contract blocker、同因 retry 和 rework budget 按当前作用域计数，不再被其他 Run 污染。
- 未知 human blocking scope 默认 fail-closed；只有明确的 side scope 才是非阻塞。
- ordinary `worker.context.warning` 保持为 Kernel 生命周期中的观察信号，不会越权触发
  第二套恢复状态机。

### 5. 当前权威驱动的 Verify、Goal 和 Dossier

- verification discovery 绑定当前 verification identity，避免消费历史 rescan。
- candidate lineage、task-map verification path 和 global rescan result 都要求当前 authority。
- Run completion profile 只汇总当前 Run 的 human、verify 和 terminal 信号。
- Goal completion 只接受当前 goal authority 的可核验证据。
- Goal Dossier 与 completion 使用同一当前权威，不再因等价但过期的历史 claim 误收敛。
- Agent 仍不能自行声明终态；缺少独立人工或验证证据时，Run 保持 active/blocked。

### 6. Web、Loop 与诊断体验

- Channel question cards、控制动作与 Workflow clarification 使用统一交互模型。
- Channel、Task、Workflow、Trace 和 Loop 在刷新与跨页后保持可恢复引用。
- Loop 可以展示恢复、阻塞和 replan 信号，但 projection 不替代 canonical state。
- Web event cache 测试与真实 workspace 分离，减少跨测试污染。
- pytest session 隔离 `ZF_WORKSPACE_HOME`，避免每个测试 Web app 预热线程扫描真实大型
  workspace；`test_web_server.py` 的运行时间从约一小时未完成降至约 25 秒。

### 7. 真实 Codex 产品 E2E

本版本使用隔离的新项目完成了以下真实链路：

1. Web 初始化并注册 Project。
2. Kanban Agent 在未知内部 id 的情况下读取可用模板与 workflow catalog。
3. 五个真实 Codex Channel 角色完成讨论，11 个 Owner 问题按 3+3+3+2 闭合。
4. Owner-confirmed PRD r2 生成带 provenance 的 canonical Task。
5. Plan/Approve Workflow 生成 scan、corrected plan、task map、source index、task docs、
   briefings、plan ports 和 candidate。
6. 候选产品 `npm test` 17/17、构建通过，Docker Playwright 11/11。
7. Dashboard 桌面与移动端跨页检查无横向溢出、永久 loading、page error 或 API 4xx/5xx。

该 E2E 最终保持 `BLOCKED`，因为 PRD 要求独立人工 WCAG 2.2 AA 证据。Agent 拒绝冒充
人工 reviewer，Run Manager 将其作为 release blocker 保存。这是预期的 fail-closed，
不是一个伪造的绿色终态。

## 已知限制

1. **人工 WCAG release gate**：完整产品 Run 仍需要独立 reviewer 生成规定证据，Agent
   不会代签人工验收。
2. **Browser runner contract**：目标项目的 Playwright gate 应显式绑定 Docker runner
   或声明宿主安装要求；否则宿主缺少 Playwright 时会正确留下历史 quality failure。
3. **Web 残余**：严格浏览器探针记录一个低风险 favicon 404；Observability 仍是较慢页面。
4. **Exactly-once 发布证明**：本轮真实 E2E 是发现问题后的 continuation，尚需在修复后的
   干净 HEAD 上再运行一次无代码修改的 release E2E。
5. **OpenCode**：可扩展 provider SPI/OpenCode native session 在本版本仅完成设计，不应
   视为已发布 provider。
6. **兼容性**：Python API、Web API、event schema、Controller profile 和部分 CLI 在 1.0
   前仍可能发生不兼容变化。

## 总结

v0.0.2 没有以更多自治掩盖交付风险。它让 ZaoFu 在真实 multi-agent 产品开发中更可靠地
