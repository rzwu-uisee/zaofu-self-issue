## v0.0.4

v0.0.4 focuses on **Task authority, product acceptance, and long-horizon recovery convergence**.
It does not add another state machine. A Task now carries one current line of authority from its
contract and execution binding through Impl/Verify, Product Acceptance, Recovery Case handling, and
Goal Closure. Dashboard, cost, and recovery projections can explain that same delivery chain.

```text
Requirement / Goal
  -> accepted artifact package + Task Map
  -> current Task contract authority + execution binding
  -> Impl / Verify receipts on immutable targets
  -> Product Acceptance report
  -> Recovery Case + bounded controlled actions when needed
  -> current Goal Closure / Goal Dossier
```

An old contract, generation, candidate, or duplicate terminal signal can no longer advance the
current Run merely because it arrived later in the event stream. Agents, Skills, and Prompts still
own semantic judgment. The Kernel enforces mechanical invariants such as schema, currentness, CAS,
leases, dispatch, evidence presence, and external effects.

## Highlights

### 1. Task Contract Authority and Execution Binding

- A durable Task authority schema, TaskStore CAS, and `TaskContractAuthorityService` make the current
  contract revision/generation a queryable and auditable authority.
- TaskAttempt, dispatch, Impl, Verify, Candidate, Judge, and terminal closure bind to the current
  execution target. Stale writes, stale results, and old verification receipts fail closed.
- Replan creates a new artifact and Task Map generation instead of hand-editing an old canonical Task.
- A real same-Task Provider A/B showed that authority/currentness supersedes old-contract output and
  completes the current generation without adding semantic rework or replan.

### 2. Product Acceptance and Recovery Cases

- `product_acceptance_spec.v1` and target-bound reports prevent a successful test process from being
  treated automatically as proof that the product goal is satisfied.
- A stable Recovery Case identity and lifecycle aggregate diagnosis, action, verification, and
  no-progress evidence for one problem, reducing duplicate effects across Supervisor, Run Manager,
  and Autoresearch.
- Run Manager now applies a one-active-effect/no-progress fence. Automated recovery must verify the
  previous action before issuing another resume or rework.
- Provider qualification receipts distinguish platform defects, missing environments, and external
  waits so unavailable Provider/browser infrastructure is not mislabeled as a semantic product failure.

### 3. Long-Horizon Recovery and Observability

- Skill lifecycle states now distinguish `considered`, `loaded`, `auto-injected`, `invoked`, and
  `missing` by role/task/attempt.
- Critic and handoff briefings consume exact artifact refs/digests, reducing duplicated large context
  while retaining required-read and currentness evidence.
- Orchestrator Agent checkpoints deduplicate the same digest/generation and expose structured decisions,
  SLA state, and admission results.
- Dashboard Long-Run Truth separates raw events from unique operations and presents current generation,
  candidate, gate, no-progress, and verified/landed/reachable/notified terminal facts.
- Read-only `zf state retention-plan --json` inventory fails closed for unknown refs, corrupt manifests,
  and still-referenced payloads. v0.0.4 does not delete runtime evidence automatically.
- Recovery was tightened for fanout replay, event rotation, gap amendments, candidate lineage, Provider
  liveness, and targeted pane termination.

### 4. Provider Usage, Budgets, and the Web Resource Plane

- Provider-neutral usage receipts normalize model, input/output, cache, reasoning, and cumulative delta
  semantics, reducing duplicate cost accounting after replay.
- The pricing catalog distinguishes estimated, reported, billed, unpriced, and partial cost. `zf cost`
  and Web use the same projection semantics.
- With a hard USD budget, unpriced usage fails closed instead of being dispatched as zero-cost work.
- Non-blocking Web read-model bootstrap/catch-up and improved Task Card, Runs, Graph, Loop, Goal Dossier,
  and cost views separate current truth, historical attempts, and terminal attention.

### 5. Controlled Pilots: Task Pipeline v4 and Orchestrator Agent

- Task Pipeline v4 implements Task Workspaces, Stage Workers, elastic placement, Impl/Verify receipts,
  incremental candidate integration, and terminal dependency freeze.
- v4 remains a `preferred: false` canary and v3 remains the default. This draft does not announce a
  general v4 rollout.
- At bounded semantic checkpoints, Orchestrator Agent can produce typed decisions, Plan adoption,
  bounded graph deltas, and targeted feedback. Kernel/WRC still owns readiness, leases, dispatch,
  transitions, and side effects.
- OA blocking/apply remains an explicit allowlisted pilot. The P15 real canary remains HOLD; OA is not
  a second scheduler or a default automatic approver.

### 6. Channel, Kanban, and Runtime Boundary Fixes

- Explicit Channel fanout mode, invalid-contribution repair, and converged-discussion selection prevent
  stale conversations from replacing the current PRD/Plan.
- Kanban Plan backend binding is no longer overwritten by a stale UI selection; successful Channel Plan
  Apply refreshes from the controlled action result.
- Workflow parent ownership, Task lifecycle timestamps, fanout package identity, and replanned Task Map
  artifact binding survive replay and recovery consistently.

## Upgrade Notes

### 1. Resolve the Version Sequence First

There is no public v0.0.3 tag and package metadata remains `0.0.2`. Release owners must either:

1. publish v0.0.3 before v0.0.4; or
2. explicitly record that v0.0.3 was skipped and align every version entry directly to `0.0.4`.

From the final candidate, update `pyproject.toml`, `src/zf/__init__.py`, `web/package.json`, and
`web/package-lock.json` together, then run:

```bash
uv sync --extra dev --extra web
npm --prefix web ci
uv run zf --version
```

The formal v0.0.4 release must report:

```text
zf 0.0.4
```

### 2. Do Not Switch Pilot Execution Paths Implicitly

- Existing PRD, Issue, and Refactor v3 profiles remain the default stable path.
- Task Pipeline v4 is enabled only in an explicit canary, shadow, or approved blocking pilot.
- Orchestrator Agent remains `exception_advisor` by default; only allowlisted pilots use
  `semantic_control`.
- Start a fresh Run when changing profiles and retain artifacts, attempts, and recovery evidence from
  the previous Run.

### 3. Validate Pricing and Budget Configuration

Read the cost projection after upgrade:

```bash
uv run zf cost
uv run zf cost --by-instance
uv run zf cost --by-backend
```

Before configuring `global_budget_usd` or role budgets, ensure that the target Provider/model resolves
in the pricing catalog. Unpriced usage blocks new dispatch when a hard budget is active.

### 4. Preserve Runtime Evidence

`zf state retention-plan --json` currently produces reclaim inventory only. Do not hand-delete active
Runs, artifact bodies, Recovery Cases, or sidecars still referenced by ref/digest.

## Known Limitations and Release Blockers

1. **Version metadata is not aligned:** it remains `0.0.2`, and v0.0.3 has no tag. Resolve the version
   sequence before publishing v0.0.4.
2. **v4 and OA remain pilots:** Task Pipeline v4 rollout is NO-GO and the OA P15 real canary is HOLD.
   Neither is announced as the default production path.
3. **No single full release matrix has run at the exact candidate:** capability batches have focused,
   mock, browser, and real Provider evidence, but these cannot be combined into one current-HEAD pass.
4. **Historical broad runs are not an all-green claim:** the Product Acceptance batch recorded
   `10398 passed, 10 failed`; seven were fixed in that batch, one SQLite WAL case passed in isolation,
   and two reproduced on the unchanged baseline. Reclassify and close from the final candidate.
5. **Real external tiers differ:** Task authority has real Provider A/B evidence; the Product Acceptance
   batch did not run a paid Provider E2E. Real Feishu outbound and WebSocket passed, but the
   human-originated inbound canary was not run and still needs a separate release drill.
6. **Retention is dry-run only:** v0.0.4 does not automatically delete runtime payloads.
7. **Developer Preview:** Python/Web APIs, event schemas, Controller profiles, and parts of the CLI may
   still change incompatibly before 1.0.

## Summary

v0.0.4 advances ZaoFu from “events can keep moving” to “only the current Task contract, current
execution target, and current acceptance evidence can close the Goal.” It also makes recovery, cost,
and Web projections more explainable while offering controlled pilots for the v4 pipeline and OA
semantic control. Those pilots do not replace the stable v3 path until they pass their release gates.
