## v0.0.1 版本

ZaoFu 是面向 long-horizon 软件交付的 AI Agent Delivery Control Plane。它不替代
Codex、Claude Code 或其他 coding agent，而是把彼此孤立的 Agent session 组织成
一套具有任务契约、持久接力、独立验证、故障恢复和操作员控制面的交付系统。

```text
idea / PRD / issue / refactor
  -> workflow intake + run goal
  -> scan / plan / task map
  -> multi-agent implementation + self-check
  -> independent verification
  -> Thin Judge + deterministic completion gate
  -> scoped delivery / bounded rework / owner escalation
```

本版本的核心承诺不是“让模型变得更聪明”，而是让 Agent 软件交付变得：

- 可配置；
- 可观察；
- 可恢复；
- 可审计；
- 由证据而非 Agent 自我声明决定是否完成。

## 首发亮点

### 1. PRD、Issue 与 Refactor 产品工作流

ZaoFu 提供三类正式产品入口：

| Controller | 适用场景 |
|---|---|
| `prd-fanout-v3.yaml` | 多模块 PRD、新功能或产品构建 |
| `prd-light-v3.yaml` | 可以容纳在单上下文中的小型 PRD |
| `issue-fanout-v3.yaml` | 跨模块 issue、bug 与回归修复 |
| `refactor-lane-v3.yaml` | 大型重构、迁移与替代式实现 |
| `*-claude.yaml` | 对应工作流的 Claude Code 版本 |

短 Controller YAML 会组合 flow profile、角色、stage topology、schema policy、
skill bundle、预算和恢复策略；项目本地 `zf.yaml` 始终是唯一有效的控制面配置。

Issue 默认也支持更轻的单任务路径。操作员可以先通过 CLI、Kanban Agent 或
Channel 澄清需求，再创建 workflow proposal 并受控启动，不需要为每个新需求
复制一份大型 YAML。

### 2. 契约化的多 Agent 执行

- 支持 Codex 与 Claude Code provider。
- 支持 tmux 与 stream-json transport。
- 支持多 lane fanout、fan-in、affinity handoff 和候选树合成。
- Impl 与 Verify 固定不可变的 TaskContract snapshot，避免验收目标在执行中漂移。
- Agent 通过结构化 result、artifact refs 和 evidence refs 返回事实，而不是仅在
  transcript 中声明“完成”。
- Provider session 可按 stage 按需启动，空闲阶段不必提前占用全部 Agent process。

### 3. 双层蜂群执行

ZaoFu v0.0.1 支持受控的 Swarm / Compound Execution：

```text
ZaoFu 外层蜂群
  task map
    -> N 个独立 lane / worker 并行执行
    -> lane affinity + durable handoff
    -> fan-in / candidate assembly
    -> independent verify

Provider 内层蜂群
  单个根 worker
    -> Codex 或 Claude Code 原生 dynamic workflow / sub-agent
    -> 并行探索、实现或审查子问题
    -> join 回根 worker
    -> 统一返回当前 task attempt 的 result + evidence
```

- 外层 lane 数量可按 Controller 和项目规模配置，适合并行处理相互独立的模块。
- 内层蜂群复用 provider 原生能力；Codex 可使用 multi-agent 与受支持模型的
  reasoning effort，Claude Code 可使用原生 sub-agent。
- 内层能力默认继承 provider/session 配置，不提供一个虚假的跨 Provider
  `swarm: true` 开关，也不保证每个任务都会创建 child agent。
- ZaoFu 以根 TaskContract、attempt、预算和 evidence 作为统一验收边界，不要求
  Kernel 接管 provider 内部的临时 child graph。
- 所有 provider-native child 必须在根 worker 返回前完成 join；其结论必须回收到
  当前 task 的 artifact/evidence，不能直接声明 workflow 完成。
- recursion guard 禁止同角色无限嵌套；内层 child 不能绕过外层 Verify、Judge、
  completion gate 或 controlled action。
- Adaptive Research 提供显式 opt-in 的只读蜂群试点，可由一个 research root
  调用有限数量的 Explore children，最终只产生一个可审计根结果。

因此，本版本的“蜂群支持”不是无边界自治或简单堆叠 Agent，而是
**可配置并发、任务边界隔离、统一证据验收、可暂停恢复**的双层执行模型。

### 4. 独立验证与证据门控交付

- Impl worker 在自己的任务边界内完成实现、自测和证据整理。
- Verify worker 独立复核 acceptance criteria、测试结果和实现证据。
- 负向验证结果会返回正确的 implementation owner，并保留原始 finding 与上下文。
- 同因 retry / rework 受 fingerprint、attempt、revision 和 cap 约束，避免无限盲重试。
- Thin Judge 只读汇总目标完成度；deterministic completion gate 复核 claim 后，
  scoped delivery 才能产生唯一的 goal 终态。
- 终态可生成 Goal Dossier，向操作员汇总目标、实现、验证、证据和交付结果。

### 5. 长程任务恢复闭环

ZaoFu 将观察、决策、诊断和状态变更拆成明确职责：

```text
failure / stall
  -> Supervisor 观察并归类
  -> Run Manager 选择有界恢复动作
  -> Controlled Action 执行
  -> post-verification
  -> resume 或 owner escalation

recurring failure fingerprint
  -> Autoresearch 复现与深度诊断
  -> 隔离的 repair proposal / backlog candidate
  -> 验证
  -> 人工或 token-gated apply
```

恢复路径支持 heartbeat、liveness、attempt identity、稳定 result envelope、
settled operation replay 和 checkpoint resume。Run Manager 处理单次运行恢复；
Autoresearch 处理重复出现的 harness 问题，两者都不能绕过 Kernel 直接改写运行真相。

### 6. 完整的本地操作面

Web Dashboard 提供：

- Workspace 与项目切换；
- Kanban、任务详情和 workflow 状态；
- Agent Sessions 与实时 provider 输出；
- Delivery Trace、Runs、Graph 和 Loop；
- Goal coverage、artifact、evidence 与 Goal Dossier；
- Inbox、人工审批和受控恢复动作；
- Channel / Group 多 Agent 讨论与 Kanban Agent；
- 成本、上下文、worker 和 projection 诊断。

CLI 覆盖配置渲染、项目初始化、workflow intake、task 与 event 查询、trace、
goal、projection、recovery、provider preflight、workspace 和 Autoresearch。

### 7. Feishu / ChatOps

- 飞书消息可以路由到 Channel、Kanban Agent、Run Manager Agent 或
  provider-backed conversation。
- Plan Ready、人工授权和恢复决策可以复用 Web 的 controlled-action 边界。
- Provider transcript、Channel body 和大 context package 使用 sidecar/ref 保存，
  不把完整聊天内容塞入事件账本。
- 外部集成只发布 intent 或请求受控动作，不成为第二控制平面。

### 8. 分层运行真相与可重建查询

| 层 | 主要载体 | 用途 |
|---|---|---|
| 控制平面 | `zf.yaml` | 期望拓扑、策略、预算、安全配置和 `project.state_dir` |
| 事件账本 | `events.jsonl` 与 archive segments | 发生顺序、因果、判定和引用 |
| 当前状态 | Task、Feature、Session、Role Session stores | 当前任务与运行状态 |
| 完整语义 | artifacts、sidecars、accepted packages | plan、task map、证据、诊断和大 payload |
| 查询投影 | SQLite、Trace、Graph、Loop、Web summaries | 快速查询与可视化，可从权威来源重建 |

Web、Feishu、Channel、Kanban Agent 和普通 worker 都不能旁路修改 canonical state。
所有状态变化与外部副作用必须经过 EventWriter、Store 或 token-gated controlled action。

### 9. 受控动态工作流与 Research

- Workflow proposal 可以从 CLI、Web、Kanban Agent 或 Channel 生成并绑定原始需求。
- Kernel 只接受已注册 flow kind 和合法 Controller，不执行任意 Agent 生成的控制逻辑。
- Agent 可以为具体项目补充 prompt、skill、plan 和 acceptance artifact，但不能成为
  第二个状态机。
- Research 支持固定角色 fanout，并提供 opt-in 的 provider-native adaptive research
  路径；研究结果仍需生成可审计 artifact 后才能进入后续工作流。

## 快速开始

### 1. 安装

```bash
git clone <repo-url> zaofu
cd zaofu

uv sync --extra dev --extra web --extra stream-json
uv run zf --version
```

预期版本：

```text
zf 0.0.1
```

### 2. 为目标项目选择 Controller

先只读检查推荐结果：

```bash
uv run zf profile bootstrap /path/to/my-project \
  --intent build \
  --backend codex \
  --scale launch
```

确认 Controller、目标项目真实 quality gates 和必需输入后再写入：

```bash
uv run zf profile bootstrap /path/to/my-project \
  --intent build \
  --backend codex \
  --scale launch \
  --apply
```

### 3. 初始化并启动

```bash
cd /path/to/my-project

uv run --project /path/to/zaofu zf init \
  --workspace-register \
  --with-bootstrap

uv run --project /path/to/zaofu zf validate --cold-start
uv run --project /path/to/zaofu zf start --dry-run --no-watch
uv run --project /path/to/zaofu zf start
```

### 4. 启动 Dashboard

```bash
cd /path/to/zaofu
tools/start-webkanban.sh --host 127.0.0.1 --port 8001
```

访问 `http://127.0.0.1:8001/`。

完整步骤见[中文快速开始](../manual/01-quickstart.md)和
[English Quick Start](../manual/01-quickstart.en.md)。

## 适用场景

ZaoFu v0.0.1 更适合：

- 多模块产品功能交付；
- 大型代码重构、语言迁移或替代式实现；
- 需要独立验证和回归证据的 issue 修复；
- 需要多个 coding agent 并行但仍要保持任务边界的项目；
- 需要外层多 lane 与 provider-native sub-agent 组合执行的蜂群任务；
- 需要暂停、恢复、审计、成本观测与人工接管的长程任务；
- 希望把重复 harness 故障沉淀为可复现诊断和改进任务的团队。

它暂时不适合：

- 只需要一次短问答或单文件编辑的任务；
- 希望完全省略项目验收标准和质量门的无人值守运行；
- 需要稳定公共 API、托管式多租户服务或生产 SLA 的场景。

## 已知限制

1. v0.0.1 是 Developer Preview。Python API、Web API、event schema、
   Controller profile 和部分 CLI 仍可能在 1.0 前发生不兼容变化。
2. ZaoFu 依赖外部 Codex CLI 或 Claude Code CLI 的安装、认证与可用性；
   provider 本身的限流、版本变化和服务故障不由 ZaoFu 控制。
3. 项目级 acceptance criteria、测试命令、构建命令和产品语义必须由目标项目提供。
   多 lane 工作流缺少真实 candidate quality gate 时会 fail-closed。
4. 真实 provider 执行会消耗模型预算，并可能修改代码、创建 worktree、运行命令或
   调用外部系统。首次运行前必须执行 validate、preflight 和 dry-run。
5. Run Manager 与 Autoresearch 提供有界恢复，不代表任意故障都能无人值守修复；
   缺少授权、高风险副作用或多次无进展时仍会升级给操作员。
6. SQLite、Web summaries 和其他 projection 可重建，但不能替代 EventLog、
   canonical stores、required artifacts 或 evidence sidecars。
7. Feishu、Channel 与外部控制动作需要额外凭证和路由配置；凭证、action token
   和 provider secret 不得提交到仓库。
8. 当前主要面向本地可信开发环境。Dashboard 默认应绑定 `127.0.0.1`，不要直接
   暴露到不可信网络。
9. 本版本不提供从内部实验 tag 或任意历史 runtime state 自动迁移的保证。升级前
   应归档 state dir，重新 render 配置并在隔离环境执行 cold-start 与 dry-run。

## 安全边界

- `zf.yaml` 是唯一控制面配置；不要硬编码或假定 state dir 一定是 `.zf/`。
- Agent 只能提交事实、artifact、evidence 和 intent，不能直接修改 Kernel 管理的真相。
- Web、API 和集成侧的 mutation 必须经过 token-gated controlled action。
- Dashboard 除非处于明确可信网络，否则只绑定 loopback。
- 不要使用 `tmux kill-server` 停止单个项目，以免终止同一主机上的其他 session。
- 启用外部 provider、飞书或无人值守执行前，请阅读
  [免责声明](../../DISCLAIMER.md)。

## 发布与兼容说明

- `v0.0.1` 是首个公开版本；公开版本语义从这里开始。
- 发布 tag 应指向通过 release validation 的确定 commit。
- 1.0 前遵循尽量兼容但允许必要破坏性调整的 Developer Preview 策略。
- Controller 或 schema 变更后，应重新 render、cold-start validate，并对目标项目
  执行隔离的 mock E2E；真实交付前再执行对应 provider 的 real E2E。

维护者在创建 `v0.0.1` tag 前至少应完成：

```bash
bash scripts/dev-premerge-gate.sh
uv run pytest -q --no-cov
npm --prefix web test
npm --prefix web run build
```

还应选择至少一个 PRD、Issue 或 Refactor Controller，完成带真实 provider 的发布
drill，并核对 plan、task map、Impl evidence、Verify verdict、Thin Judge claim、
delivery result、Goal Dossier、restart/resume 和最终 goal terminal state。

## 总结

ZaoFu v0.0.1 建立了一个可以运行的 multi-agent harness engineering 基线：
Agent 负责规划、实现、独立验证和语义判断；确定性 Kernel 负责身份、状态、
证据、恢复、交付与副作用边界；操作员可以通过 Web、CLI 或 Feishu 观察并接管。

这是第一个公开起点，而不是稳定终点。v0.0.1 已具备承载真实 PRD、Issue 和
Refactor 交付试验的完整产品骨架，同时仍要求项目级适配、真实质量门和发布前
provider drill。
