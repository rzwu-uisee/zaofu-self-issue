## v0.0.6 版本

v0.0.6 聚焦 **可控的人机协作收口、可解释的运行观测，以及受证据约束的能力积累**。
它将 Channel/Kanban Agent 中的可见对话、人工决策和 Provider 完整性进一步分层；新增默认关闭的
OTLP/Operations 观测面，将 Web 诊断收敛到有界 Trace/Span 与按上下文加载的 Delivery/Loop，
并把 Autoresearch 的已验证 Learn 结果接入可比较、可回退的 Evolution 生命周期。

```text
可见对话 / 人工决策
  -> EventLog + sidecar + controlled action
  -> Task / Gate / Delivery 的既有权威边界

已验证的 Learn Run
  -> immutable attempt + environment snapshot
  -> baseline / candidate / independent canary
  -> retained asset 或 revoked
```

这不是让 Web、监控系统或 Agent 获得 Task/Gate 的写权。Channel、Observability 和 Evolution
继续通过事件、artifact 与受控动作与 Kernel 协作，不能成为第二个 canonical state machine。

## 发布亮点

### 1. Channel 与 Kanban Agent 的决策和流式回复更可控

- Channel 将执行状态与人工注意力分为两条只读轴：Agent 仍在回复时，页面会同时呈现正在响应的
  Agent 与待决策项；只有执行范围确实等待 Owner 时才进入 `Waiting for you`。
- `Operator Inbox -> Decisions` 聚合当前 Channel owner question 和 Kanban Agent plan request，
  但只提供回到原始对话的深链。实际回答继续经过原有的 question/plan 受控入口。
- Channel 的可见 Markdown 与机器 `channel_contribution` 合同分离；Kanban Agent 的
  `plan_request`、`action_proposal` 控制块不会先作为 JSON 闪现在聊天中。控制块识别后显示
  Preparing 状态，canonical request 到达后才替换为可操作卡片。
- Provider 输出不完整或缺少必需 typed contract 时，Channel 会执行有界 continuation，而不是把
  不完整回复直接作为讨论结论。完整 raw reply、typed contract 和 artifact 仍保留用于审计与重放。

### 2. Provider 与运行可观测性成为独立、可关闭的运维面

- 新增 provider capability、受管 Claude Code per-turn telemetry、脱敏 Runtime Logs、
  Operations 摘要、低基数 Prometheus `/metrics`、OTLP/HTTP synthetic span exporter 和
  attention 投影。
- OTLP exporter 从 EventLog 的只读投影异步发送，使用有界 batch、cursor、idempotency key、
  backoff 与采样策略。collector 故障只产生可诊断 health/backlog，不阻塞 EventWriter、
  Provider dispatch 或 Workflow。
- Traces 使用有界 list/detail/cursor 合同；选择 Trace 后才加载 lifecycle Span、Execution 和 Event
  evidence，单条 Raw 证据继续按需读取。Span 只来自 allowlist 生命周期事件对，并显式报告
  coverage、provenance 与 degraded 原因，不把普通 Event timeline 或 synthetic OTLP span 伪装成
  Provider-native Span。
- Web 退役独立 Runtime Logs panel 与顶层 Raw 入口；脱敏日志 store、有界 HTTP API、轮转和审计
  能力继续保留。Operations 继续作为兼容运维入口，Provider/OTLP/Prometheus 能力没有被删除。
- Delivery 保持 Overview/Runs/Graph 的 view-scoped 投影，Work 只在选择 Goal 后加载；Loop 使用独立
  投影和持久缓存。Trace/Span/Event 是诊断证据，Delivery/Task/Gate 仍是业务事实入口。
- 端点、header 和 token 只从环境变量读取；Prompt、回复、tool body、绝对路径和 secret 不进入
  metric label 或 exporter attribute。Web read API 保持 project-scoped、bounded、redacted，并可
  返回诊断所需的 Task/Trace identity；这些高基数 ID 不会被提升为 metric label。

### 3. Autoresearch 到自我进化的证据闭环

- 已验证的 Learn Run 通过 Run Archive 中唯一的 typed deposition 进入 immutable campaign 和
  evolution attempt；普通 Event 文本、聊天投影或未归档回复不能直接被提升为能力。
- baseline/candidate 使用冻结的 evaluator、provider、toolchain、environment、sandbox、network、
  credential-policy 等比较身份。缺 CLI、认证、sealed evaluator、凭据能力或环境漂移会在调用
  Provider 前终止为明确证据，不会被误记为 candidate 质量失败或无限重试。
- 资产需要经过重复 trial、sealed evaluator、独立 canary 和 receipt-bound 状态转换后，才可进入
  `active_retained`；负迁移、冲突或证据不足可被撤销。
- `auto_low_risk` 仅在显式启用时可自动保留 allowlist 中的 `memory_entry`、`runbook`、
  `regression_fixture`。`framework_code`、`workflow_config`、`provider_route` 与
  `tool_capability` 继续保持 proposal-only，必须由对象特定 Owner 批准和 apply。

### 4. 有界的执行策略演进与开发辅助能力

- Run Manager 可针对结构化 provider/capability/context 失败，在预批准的静态 route catalog 内
  为同一 Task Owner 选择一次有界 execution-route switch，并写入绑定 Task、Run、checkpoint 与
  policy digest 的 receipt。它不会动态发明 Provider、模型、权限或工具范围。
- 新增 `zf-find-simplifications` 与 `zf-record-browser-demo` Skills：前者以 consumer/protected
  seam 证据提出简化建议，后者以 Docker Playwright 的可复现帧、GIF 与 provenance 记录浏览器
  工作流。两者均不绕过既有测试、Owner gate 或发布流程。

## 从 v0.0.5 到 v0.0.6

从 `v0.0.5` 到 `v0.0.6`：

- 20 个提交，均为单父提交；
- 257 个文件变化，新增 29,932 行、删除 1,265 行；
- 主要涉及 80 个 `src/zf/` 文件、23 个 `web/src/` 文件、Provider/OTLP 与 Evolution 的
  确定性和真实 Provider E2E 测试、Skills，以及中英文操作手册。

这些数字包含测试、任务记录、报告、手册、Skills 和二进制文档资产，不等同于净产品代码量。
发布质量应以受控交互、事件/证据权威、可观察性隔离和真实 Provider 验证为准。

Trace、Delivery、Loop 收敛工作尚未进入最终发布 merge，因此上述数字不是 v0.0.6 最终 delta。
正式候选确定后必须从 `bccf76dc` 到最终 merge SHA 重新计算提交数、文件数和增删行。

## 升级说明

1. **保持默认关闭**：不配置 `observability` 或 `runtime.evolution` 时，新能力不会自动启动
   collector、exporter、自动采纳或修改现有项目行为。
2. **更新依赖和 Web 资源**：部署更新后执行 `uv sync --extra dev --extra web`、
   `npm --prefix web ci`、`npm --prefix web run build`，然后重启 runtime 与 Web Dashboard。
3. **不手工迁移业务真相**：不要编辑 `events.jsonl`、Task/Feature store、Channel sidecar 或
   `capabilities.json` 来修复页面或调整资产状态。新投影应由运行时和受控命令重建。
4. **先在隔离环境启用观测/进化**：使用 `/tmp/zf-<purpose>-<utc>/`、可控 collector 和最小
   policy canary 验证 environment preflight、脱敏、token gate、backoff、比较与回退后再扩大范围。
5. **保留 Provider 边界**：受管原生 telemetry 当前只对可安全 per-turn 注入的 Claude Code
   headless/stream-json route 宣称支持；Codex 目前只报告 capability/probe 状态，ZaoFu
   synthetic OTLP span 不能被视为 Codex 原生 trace。
6. **使用新的诊断入口**：业务因果优先进入 Traces；进程/transport/sidecar 诊断通过 Runtime
   Logs 有界 API 读取。旧深链继续做兼容归一，但独立 Runtime Logs Web panel 不再提供。

## 已知限制

1. **Evolution 是 partial capability**：它不是模型训练，也不会默认改写源码、配置、Skills 或
   主分支。高风险资产仍需要 proposal、Owner approval 和受控 apply。
2. **上下文与普通 Memory 不是完整历史重放器**：普通 Memory 的 `max_days` 仍是元数据，
   并非逐项严格 expiry/applicability gate；长期复用应检查 retained asset 的 scope、证据、
   conflict 与 usage outcome。
3. **外部 telemetry rollout 仍需独立 canary**：fake collector 与受控 route 测试不能证明某个
   实际 Collector、Claude/Codex 版本或宿主网络的端到端遥测协议完全可用。
4. **Span coverage 不等于 Provider-native tracing**：当前 Web Span 是 allowlist lifecycle event
   pair 的有界投影；`collector=unobserved` 单独说明没有 Provider collector 证据，事件不完整、
   不可信或 timing 退化时 coverage 才会 degraded。两者都不能证明已采集 Provider 内部完整调用树。
5. **公开投影保留 22 个已分类 deterministic 基线/宿主红项**：10 个 Codex hook hash
   version sensor、2 个固定假路径 host preflight、9 个引用公开投影缺失文件的测试，以及 1 个
   sim1 `base_commit` 不一致。相同节点已在 detached `dev@ffe4d43` 全部复现；发布验证未改写
   hash/version 基线，也未恢复清单明确排除的私有文件。
6. **npm 开发工具链仍有审计项**：production dependency audit 为 0 high、1 low；完整 audit
   的 3 个 high 位于 Babel/PostCSS/Vite/nanoid 等开发构建路径。本版本不自动执行可能扩大
   lockfile 变更面的 `npm audit fix`。
7. **Developer Preview**：Web/API、事件 schema、Provider capability 和交互合同在 1.0 前
   仍可能发生不兼容变更。

## 总结

v0.0.6 不是以更多 Agent 自治替代工程约束。它让多 Agent 对话中的可见回答、人工决策和
机器合同更清晰，让运行健康信号可观测但不篡改交付真相，并让经过验证的经验在明确的评估、
环境与回退边界内积累为可复用能力。
