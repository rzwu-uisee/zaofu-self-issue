## v0.0.4 版本

v0.0.4 聚焦 **Task 权威、产品验收和 Long-Horizon 恢复收敛**。这一版本不是增加一套
平行状态机，而是让同一个 Task 从当前合同、执行绑定、Impl/Verify、Product Acceptance、
Recovery Case 到 Goal Closure 始终引用同一代权威事实，并让 Dashboard、成本和恢复动作
能够解释这条交付链。

```text
Requirement / Goal
  -> accepted artifact package + Task Map
  -> current Task contract authority + execution binding
  -> Impl / Verify receipts on immutable targets
  -> Product Acceptance report
  -> Recovery Case + bounded controlled actions when needed
  -> current Goal Closure / Goal Dossier
```

旧合同、旧 generation、旧 candidate 或重复 terminal 信号不能再仅凭事件顺序推进当前
Run。语义判断仍由 Agent、Skill 和 Prompt 负责；Kernel 只执行 schema、currentness、CAS、
lease、dispatch、证据存在性和外部副作用等机械约束。

## 发布亮点

### 1. Task Contract Authority 与执行绑定

- 引入可持久化的 Task authority schema、TaskStore CAS 和统一的
  `TaskContractAuthorityService`，把当前合同 revision/generation 变成可查询、可审计的唯一
  权威入口。
- TaskAttempt、dispatch、Impl、Verify、Candidate、Judge 和 terminal closure 都必须绑定当前
  execution target；stale write、stale result 和旧 verification receipt 采用 fail-closed。
- replan 会产生新的 artifact/Task Map generation，不再通过手工改写旧 Task 合同来“修正”
  当前事实。
- 同任务真实 Provider A/B 表明：启用 authority/currentness 后，旧合同结果会被 supersede，
  当前 generation 能在不增加 semantic rework/replan 的情况下完成。

### 2. Product Acceptance 与 Recovery Case

- 增加 `product_acceptance_spec.v1` 和绑定当前 target 的验收报告；Goal Closure 不再把
  “测试进程退出成功”直接等同于“产品已满足目标”。
- Recovery Case 使用稳定 identity 和生命周期，聚合同一问题的诊断、动作、验证和
  no-progress 证据，避免 Supervisor、Run Manager 与 Autoresearch 对同一故障重复施加效果。
- Run Manager 增加 one-active-effect/no-progress fence；自动恢复必须先验证上一个动作结果，
  不能持续盲目 resume/rework。
- Provider qualification receipt 区分平台缺陷、环境缺失和外部等待；不可用的 Provider 或
  浏览器环境不会被误记为产品语义失败。

### 3. Long-Horizon 恢复与可观测性

- Skill 生命周期区分 `considered`、`loaded`、`auto-injected`、`invoked` 和 `missing`，按
  role/task/attempt 投影，避免“配置了 Skill”被误报为“实际执行了 Skill”。
- Critic 与接力 briefing 通过精确 artifact ref/digest 读取正文，减少重复嵌入大上下文，
  同时保留 required-read 和 currentness 证据。
- Orchestrator Agent checkpoint 对同 digest/generation 去重，并记录结构化 decision、SLA 和
  admission 结果。
- Dashboard Long-Run Truth 区分 raw event 与 unique operation，显示当前 generation、
  candidate、gate、no-progress、verified/landed/reachable/notified 等终态事实。
- 增加只读 `zf state retention-plan --json` inventory；未知 ref、损坏 manifest 和仍被引用的
  payload 均 fail-closed。本版本不自动删除运行时证据。
- fanout replay、event rotation、gap amendment、candidate lineage、provider liveness 和 pane
  定向终止的恢复路径得到收敛。

### 4. Provider 用量、预算与 Web 资源平面

- Provider-neutral usage receipt 统一记录模型、输入/输出、cache、reasoning 和 cumulative
  delta，降低重放或累计统计造成的重复计费。
- Pricing catalog 区分 estimated、reported、billed、unpriced 和 partial cost；`zf cost` 与
  Web 使用同一投影口径。
- 配置硬美元预算时，无法定价的用量会 fail-closed，而不是被当作零成本继续 dispatch。
- Web read model bootstrap/catch-up 改为非阻塞资源加载；Task Card、Runs、Graph、Loop、Goal
  Dossier 和成本视图更明确地区分当前事实、历史尝试和需要关注的终态。

### 5. 受控试点：Task Pipeline v4 与 Orchestrator Agent

- Task Pipeline v4 已实现 Task Workspace、Stage Worker、弹性 placement、Impl/Verify receipt、
  incremental candidate integration 和 terminal dependency freeze。
- v4 仍是 `preferred: false` 的 canary，v3 仍为默认路径；本草案不宣布 v4 全量切换。
- Orchestrator Agent 可在受控 semantic checkpoint 产出 typed decision、Plan adoption、bounded
  graph delta 或 targeted feedback，但 Kernel/WRC 继续拥有 readiness、lease、dispatch、
  transition 和 side effect 权限。
- OA blocking/apply 仍采用显式 pilot/allowlist；P15 real canary 保持 HOLD，不能把 OA 当作
  第二个调度器或默认自动审批者。

### 6. Channel、Kanban 与运行边界修复

- Channel fanout mode、无效 contribution 修复和已收敛讨论选择更加确定，避免旧讨论覆盖当前
  PRD/Plan。
- Kanban Plan 的后端绑定不再被 stale UI selection 改写；Channel Plan Apply 成功后按受控
  action 结果刷新。
- workflow parent ownership、Task 生命周期时间戳、fanout package identity 和 replanned Task
  Map 的 artifact 绑定在 replay/recovery 后保持一致。

## 升级说明

### 1. 先收口版本序列

当前仓库没有公开的 v0.0.3 tag，包元数据仍为 `0.0.2`。发布负责人必须选择其一：

1. 先正式发布 v0.0.3，再发布 v0.0.4；或
2. 明确记录跳过 v0.0.3，并直接把所有版本入口升级为 `0.0.4`。

无论选择哪条路径，都应从最终候选提交统一更新 `pyproject.toml`、`src/zf/__init__.py`、
`web/package.json` 和 `web/package-lock.json`，然后执行：

```bash
uv sync --extra dev --extra web
npm --prefix web ci
uv run zf --version
```

正式 v0.0.4 应输出：

```text
zf 0.0.4
```

### 2. 不要隐式切换试点执行路径

- 现有 PRD、Issue 和 Refactor v3 profile 继续作为默认稳定路径。
- Task Pipeline v4 只在显式 canary/shadow/approved blocking pilot 中启用。
- Orchestrator Agent 默认保持 `exception_advisor`；只有 allowlist pilot 才启用
  `semantic_control`。
- 切换 profile 应启动 fresh Run 并保留旧 Run 的 artifact、attempt 和 recovery evidence。

### 3. 校验预算和定价配置

升级后先读取成本投影：

```bash
uv run zf cost
uv run zf cost --by-instance
uv run zf cost --by-backend
```

配置 `global_budget_usd` 或角色预算前，应确保目标 Provider/model 在 pricing catalog 中可
解析；硬预算下的 unpriced usage 会阻止新 dispatch。

### 4. 保留运行证据

`zf state retention-plan --json` 目前只生成可回收 inventory。不要手工删除 active Run、
artifact body、Recovery Case 或仍被 ref/digest 引用的 sidecar。

## 已知限制与发布阻断项

1. **版本元数据未升级**：当前仍为 `0.0.2`，且 v0.0.3 未打 tag；正式 v0.0.4 发布前必须
   先处理版本序列。
2. **v4 与 OA 仍是试点**：Task Pipeline v4 rollout 为 NO-GO，OA P15 real canary 为 HOLD；
   本草案不把两者声明为默认生产路径。
3. **最终候选尚未执行单次完整 release matrix**：不同能力批次有明确 focused、mock、
   browser 和真实 Provider 证据，但不能拼接成当前 HEAD 的一次完整通过声明。
4. **历史 broad run 不能冒充全绿**：Product Acceptance 批次曾记录
   `10398 passed, 10 failed`；其中 7 项在该批修复，1 项 SQLite WAL 隔离通过，2 项可在未
   修改基线复现。正式发布必须从最终候选重新分类并收口。
5. **真实外部验证不等价**：Task authority 已有真实 Provider A/B；Product Acceptance
   批次未执行收费 Provider E2E。Feishu 真实出站与 WebSocket 已通过，但真人发起的入站
   canary 未执行，仍需单独 release drill。
6. **Retention 仅 dry-run**：本版本不会自动清理 runtime payload。
7. **Developer Preview**：Python/Web API、event schema、Controller profile 与部分 CLI
   在 1.0 前仍可能不兼容变化。

## 总结

v0.0.4 把 ZaoFu 的交付主线从“事件能够继续流转”提升到“只有当前 Task 合同、当前执行
目标和当前验收证据才能完成 Goal”。它同时增强恢复、成本和 Web 可解释性，并提供 v4
pipeline 与 OA semantic control 的受控试点；这些试点在完成真实 release gate 前不会替代
现有 v3 稳定路径。
