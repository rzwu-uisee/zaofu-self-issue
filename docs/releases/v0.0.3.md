## v0.0.3 版本

v0.0.3 把 v0.0.2 已有的 Channel、PRD、Task 与受控 Workflow 交付路径延伸到
**Project 级 Feishu 协作群**。重点不是让飞书成为第二个控制面，而是把群消息、卡片、
审批、运行状态和长文本投影纳入同一条 EventWriter、受控动作和可回读证据链。

```text
Project Feishu 群
  -> 精确 (app_id, chat_id) 路由到 Project
  -> Kanban Agent / Run Manager 受控处理
  -> Channel / PRD / Task proposal
  -> Owner 确认的 Plan / Workflow action
  -> ZaoFu Event / Artifact / Delivery evidence
  -> 飞书进度与结果投影
```

消息本身不直接创建 canonical Task、启动 Workflow 或修改 `events.jsonl` 以外的
canonical 状态。所有外部副作用仍通过受控 CLI、callback 验签和 Kernel 生命周期执行。

## 发布亮点

### 1. Project Feishu 协作群与多 Workspace Bridge

- 每个 Project 可以拥有一个显式管理的 Feishu 协作群，binding 保存为项目运行时
  sidecar，Workspace 只维护可重建的精确路由索引。
- 默认 `auto_provision: false`：`zf init` 只注册 Project 并创建 `pending` binding，
  不会隐式创建真实飞书群。
- 只有显式的 `auto_provision: true` 或
  `zf feishu group provision --confirm` / `attach --confirm` 才会调用飞书；随后必须回读
  Owner 和所有配置 bot，失败会停在 `repair_required`，不会伪造 `active`。
- 同一主机、同一 Feishu App 只维持一条 WebSocket。多个 Workspace / Project 通过租约
  共享它，入站消息按精确 `(app_id, chat_id)` 选择 Project，不使用 wildcard fallback。
- 群内真实成员是 Owner、Kanban Agent App bot 与 Run Manager App bot；Codex、Claude
  Code、OpenClaw 等内部 Channel 成员由这些 bot 代理，不会伪装成飞书 App 成员。

### 2. 飞书到受控交付的闭环

- Project 群中的普通消息默认交给 `primary_responder`；显式 @ Kanban Agent 或
  Run Manager 时路由到对应 target。
- Kanban Agent 能用 canonical projection 回答项目状态，不必为了读取状态启动 Provider
  run；回复仍写入同一条 Channel 消息与完成事件生命周期。
- Channel / PRD / Task 和 Workflow 的请求保留为可审计 proposal。Plan 问题与审批通过
  飞书卡片交付，Owner 的确认才允许受控 action 进入 `workflow.invoke.requested`。
- Workspace bridge 的 catch-up cursor、idempotency 和 project binding 分开保存，重启后
  不会混淆不同项目的消息、thread 或 agent session。

### 3. 可读的回复卡片与可靠的流式投影

- 回复、进度、问题、交付和失败信号都使用面向人的飞书卡片，而不是把内部 event JSON
  直接暴露给群成员。
- 入站 replay、异步 dispatch、stream completion 和最终交付卡采用幂等关联，避免一次
  Agent 回复出现重复的完成卡。
- 长 PRD、评审和扫描结果保留在 ZaoFu Channel / artifact sidecar；飞书卡片显示摘要和
  可操作状态，不把聊天卡当作无限长度的证据存储。

### 4. Feishu / lark-cli 运维契约收紧

- Project 群管理固定使用受限的 `lark-cli` argv；secret 仅经环境传递，不写入 binding
  或命令参数。
- 群创建、成员回读和补齐要求 `im:chat:create`、`im:chat.members:read`、
  `im:chat.members:write_only`，并要求 `lark-cli >= 1.0.64`。
- Docx / Base 的 Automation 和 Kanban 同步仍是只读投影的外部发布端口，不会从飞书反向
  改写 Task、Kanban 或 EventLog。

## 发布能力合同

- Authority / 权限边界: Feishu 只是交互与投影 surface；入站意图经 EventWriter，外部写入经受控 action / `lark-cli` adapter，Provider Agent 没有 action token。

## 从 v0.0.2 到 v0.0.3

对比 `v0.0.2`，主要增量集中在 Feishu Project group binding、workspace bridge lease、
入站 catch-up、Kanban Agent 状态回应、Plan/Delivery card 和 Channel stream 的幂等收敛。

这不是新的平行调度器：Task、Workflow、Run、Channel、Artifact 和 EventLog 的 canonical
owner 没有变化。Feishu 只能请求或投影受控状态。

## 升级说明

### 1. 安装并确认版本

包、CLI 和 Web 版本元数据已统一到 `0.0.3`。从 release checkout 重新安装依赖后再进行
本地验证：

```bash
uv sync --extra dev --extra web --extra feishu
npm --prefix web ci
uv run zf --version
```

预期：

```text
zf 0.0.3
```

### 2. 启用 Project Feishu 协作群

先保持默认的无外部写入路径并回读 binding：

```bash
uv run zf init --workspace default
uv run zf feishu group status
lark-cli --version
```

确认 Owner 的 app-scoped open_id、两个 bot 凭据、权限和 `lark-cli >= 1.0.64` 后，才使用
`auto_provision: true` 或 `zf feishu group provision --confirm`。已有飞书群应使用
`zf feishu group attach --chat-id <chat_id> --confirm`，不要手工写入 runtime `chat_id`。

### 3. 兼容性

- 现有未启用 `feishu_project_group` 的项目继续使用 `integrations.feishu_routing`。
- 不要为同一 App 单独启动多个 debug bridge；受管 sidecar 使用 host/App singleton lock。
- Developer Preview 阶段的 Python API、Web API、event schema、Controller profile 和部分
  CLI 仍可能在 1.0 前不兼容变化。

## 已知限制

1. **真实飞书 E2E 依赖目标 tenant 权限**：本轮 Project group / bridge 通过
   deterministic mock、集成和 post-merge 回归验证；真实 App 仍建议由拥有目标 tenant
   权限的操作员完成隔离 Workspace 的建群、入站、审批和回读测试。
2. **跨 App open_id**：Owner open_id 必须对 provisioner App 可见；否则飞书会返回
   `open_id cross app`，binding 将保持 `repair_required`。
3. **群成员模型**：内部 Coding Agent 不是独立飞书机器人，不能直接 @；应通过 Kanban
   Agent 或 Run Manager 代理的 Channel 角色协作。
4. **长文本边界**：飞书卡片不会自动拆分成长文或创建飞书文档；审计正文和大证据仍在
   ZaoFu artifact sidecar / Channel 中。

## 总结

v0.0.3 把 Feishu 从单纯通知入口推进为 Project 级、可回读、可恢复的协作界面，同时保持
ZaoFu 的确定性 Kernel 仍是唯一控制面。群消息能够推动讨论和受控交付，但不会绕过 Owner
确认、action token、事件账本或独立验证。
