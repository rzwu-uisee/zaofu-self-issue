## v0.0.1

ZaoFu is an AI Agent Delivery Control Plane for long-horizon software
delivery. It does not replace Codex, Claude Code, or another coding agent.
Instead, it organizes isolated agent sessions into a delivery system with task
contracts, durable handoffs, independent verification, failure recovery, and
operator control.

```text
idea / PRD / issue / refactor
  -> workflow intake + run goal
  -> scan / plan / task map
  -> multi-agent implementation + self-check
  -> independent verification
  -> Thin Judge + deterministic completion gate
  -> scoped delivery / bounded rework / owner escalation
```

This release does not promise a smarter model. It makes agentic delivery:

- configurable;
- observable;
- recoverable;
- auditable;
- complete only when supported by evidence, not when an agent says it is done.

## Release Highlights

### 1. Product Workflows for PRDs, Issues, and Refactors

ZaoFu provides three production workflow families:

| Controller | Use case |
|---|---|
| `prd-fanout-v3.yaml` | Multi-module PRDs, new features, and product builds |
| `prd-light-v3.yaml` | Small PRDs that fit in a single context |
| `issue-fanout-v3.yaml` | Cross-module issues, bugs, and regression repairs |
| `refactor-lane-v3.yaml` | Large refactors, migrations, and replacement implementations |
| `*-claude.yaml` | Claude Code variants of the same workflows |

Short Controller YAML files compose flow profiles, roles, stage topology,
schema policy, skill bundles, budgets, and recovery policy. A project-local
`zf.yaml` remains the only active control-plane configuration.

Issues also support a lighter single-task path by default. Operators can
clarify a request through the CLI, Kanban Agent, or a Channel, then create and
start a controlled workflow proposal without copying a large YAML file for
every request.

### 2. Contracted Multi-Agent Execution

- Codex and Claude Code providers.
- tmux and stream-json transports.
- Multi-lane fanout, fan-in, affinity handoff, and candidate assembly.
- Immutable TaskContract snapshots for Impl and Verify, preventing acceptance
  targets from drifting during execution.
- Structured results, artifact refs, and evidence refs instead of
  transcript-only completion claims.
- Stage-scoped provider sessions that start on demand, so idle stages do not
  need to reserve every agent process in advance.

### 3. Two-Level Swarm Execution

ZaoFu v0.0.1 supports controlled Swarm / Compound Execution:

```text
ZaoFu outer swarm
  task map
    -> N independent lanes / workers in parallel
    -> lane affinity + durable handoff
    -> fan-in / candidate assembly
    -> independent verify

Provider inner swarm
  one root worker
    -> Codex or Claude Code native dynamic workflow / sub-agent
    -> parallel exploration, implementation, or review
    -> join back into the root worker
    -> one result + evidence package for the current task attempt
```

- The Controller and project scale determine the number of outer lanes,
  allowing independent modules to run in parallel.
- The inner swarm reuses provider-native capabilities. Codex can use
  multi-agent execution and supported reasoning effort levels; Claude Code can
  use native sub-agents.
- Inner capabilities inherit provider/session configuration. ZaoFu does not
  invent a misleading cross-provider `swarm: true` switch, and it does not
  guarantee that every task creates child agents.
- The root TaskContract, attempt, budget, and evidence remain the acceptance
  boundary. The Kernel does not need to own the provider's temporary child
  graph.
- The root-worker contract requires every provider-native child to join before
  the root returns. Child findings must be included in the current task's
  artifacts and evidence and cannot directly declare the workflow complete.
- The recursion guard prevents unbounded same-role nesting. Inner children
  cannot bypass outer Verify, Judge, the completion gate, or controlled
  actions.
- Adaptive Research provides an explicit opt-in, read-only swarm pilot. One
  research root may use a bounded number of Explore children and must return
  one auditable root result.

Swarm support in this release is therefore not unbounded autonomy or a larger
pile of agents. It is a two-level model with **configurable concurrency,
isolated task boundaries, unified evidence-based acceptance, and durable
pause/resume behavior**.

### 4. Independent Verification and Evidence-Gated Delivery

- An Impl worker implements, self-tests, and packages evidence within its task
  boundary.
- An independent Verify worker checks acceptance criteria, test results, and
  implementation evidence.
- A negative verdict returns to the correct implementation owner with the
  original findings and context intact.
- Fingerprints, attempts, revisions, and caps bound equivalent retries and
  rework instead of permitting infinite blind loops.
- Thin Judge performs a read-only synthesis of goal completion. Scoped
  delivery can produce the single terminal goal state only after the
  deterministic completion gate validates the claim.
- A terminal run can produce a Goal Dossier that summarizes the goal,
  implementation, verification evidence, and delivery result for the
  operator.

### 5. Long-Horizon Recovery

ZaoFu separates observation, decision-making, diagnosis, and state mutation:

```text
failure / stall
  -> Supervisor observes and classifies
  -> Run Manager selects a bounded recovery action
  -> Controlled Action applies it
  -> post-verification
  -> resume or owner escalation

recurring failure fingerprint
  -> Autoresearch reproduces and diagnoses
  -> isolated repair proposal / backlog candidate
  -> verification
  -> human- or token-gated apply
```

Recovery paths cover heartbeat, liveness, attempt identity, stable result
envelopes, settled-operation replay, and checkpoint resume. Run Manager
recovers an individual run; Autoresearch investigates recurring harness
failures. Neither may bypass the Kernel and directly rewrite runtime truth.

### 6. Complete Local Operator Surfaces

The Web Dashboard provides:

- Workspace and project switching;
- Kanban, task details, and workflow status;
- Agent Sessions and live provider output;
- Delivery Trace, Runs, Graph, and Loop views;
- goal coverage, artifacts, evidence, and Goal Dossiers;
- Inbox, human approval, and controlled recovery actions;
- Channel / Group multi-agent discussions and Kanban Agent;
- cost, context, worker, and projection diagnostics.

The CLI covers configuration rendering, project initialization, workflow
intake, task and event queries, trace, goal, projection, recovery, provider
preflight, workspace operations, and Autoresearch.

### 7. Feishu / ChatOps

- Feishu messages can route to a Channel, Kanban Agent, Run Manager Agent, or a
  provider-backed conversation.
- Plan Ready, human authorization, and recovery decisions reuse the same
  controlled-action boundary as the Web interface.
- Provider transcripts, Channel bodies, and large context packages are stored
  as sidecars and refs instead of being embedded in the event ledger.
- External integrations publish intent or request a controlled action; they do
  not become a second control plane.

### 8. Layered Runtime Truth and Rebuildable Queries

| Layer | Primary carrier | Purpose |
|---|---|---|
| Control plane | `zf.yaml` | Desired topology, policy, budgets, security, and `project.state_dir` |
| Event ledger | `events.jsonl` and archive segments | Occurrence order, causation, verdicts, and refs |
| Current state | Task, Feature, Session, and Role Session stores | Current task and runtime state |
| Complete semantics | Artifacts, sidecars, and accepted packages | Plans, task maps, evidence, diagnostics, and large payloads |
| Query projections | SQLite, Trace, Graph, Loop, and Web summaries | Fast queries and visualization rebuilt from authoritative sources |

Web, Feishu, Channel, Kanban Agent, and ordinary workers cannot bypass these
boundaries to mutate canonical state. State transitions and external side
effects must flow through EventWriter, a canonical Store, or a token-gated
controlled action.

### 9. Controlled Dynamic Workflows and Research

- Workflow proposals can originate from the CLI, Web, Kanban Agent, or a
  Channel and remain bound to the source request.
- The Kernel accepts only registered flow kinds and valid Controllers. It does
  not execute arbitrary control logic generated by an agent.
- Agents may add project-specific prompts, skills, plans, and acceptance
  artifacts, but they do not become a second state machine.
- Research supports fixed-role fanout and an opt-in provider-native adaptive
  research path. Results must still produce auditable artifacts before they
  can enter a downstream workflow.

## Quick Start

### 1. Install

```bash
git clone <repo-url> zaofu
cd zaofu

uv sync --extra dev --extra web --extra stream-json
uv run zf --version
```

Expected version:

```text
zf 0.0.1
```

### 2. Select a Controller for the Target Project

Inspect the recommendation without changing the target project:

```bash
uv run zf profile bootstrap /path/to/my-project \
  --intent build \
  --backend codex \
  --scale launch
```

After reviewing the Controller, the target project's real quality gates, and
all required inputs, apply it:

```bash
uv run zf profile bootstrap /path/to/my-project \
  --intent build \
  --backend codex \
  --scale launch \
  --apply
```

### 3. Initialize and Start

```bash
cd /path/to/my-project

uv run --project /path/to/zaofu zf init \
  --workspace-register \
  --with-bootstrap

uv run --project /path/to/zaofu zf validate --cold-start
uv run --project /path/to/zaofu zf start --dry-run --no-watch
uv run --project /path/to/zaofu zf start
```

### 4. Start the Dashboard

```bash
cd /path/to/zaofu
tools/start-webkanban.sh --host 127.0.0.1 --port 8001
```

Open `http://127.0.0.1:8001/`.

See the [Chinese Quick Start](../manual/01-quickstart.md) and
[English Quick Start](../manual/01-quickstart.en.md) for the complete path.

## Intended Use

ZaoFu v0.0.1 is a better fit for:

- multi-module product delivery;
- large code refactors, language migrations, and replacement implementations;
- issue repair that requires independent verification and regression evidence;
- projects that need several coding agents in parallel without losing task
  boundaries;
- swarm tasks that combine outer lanes and provider-native sub-agents;
- long-running work that needs pause, resume, audit, cost visibility, and
  human takeover;
- teams that want recurring harness failures to become reproducible diagnoses
  and improvement work.

It is not currently intended for:

- one short question or a single-file edit;
- unattended runs that omit project acceptance criteria and quality gates;
- stable public APIs, hosted multi-tenant services, or production SLA
  requirements.

## Known Limitations

1. v0.0.1 is a Developer Preview. The Python API, Web API, event schemas,
   Controller profiles, and parts of the CLI may change incompatibly before
   1.0.
2. ZaoFu depends on the installation, authentication, and availability of an
   external Codex CLI or Claude Code CLI. Provider rate limits, version
   changes, and service outages are outside ZaoFu's control.
3. The target project must provide its acceptance criteria, test commands,
   build commands, and product semantics. A multi-lane workflow without a real
   candidate quality gate fails closed.
4. Real provider execution consumes model budget and may modify code, create
   worktrees, run commands, or call external systems. Run validation,
   preflight, and a dry run before the first real execution.
5. Run Manager and Autoresearch provide bounded recovery, not a guarantee that
   every failure can be repaired without an operator. Missing authorization,
   high-risk side effects, or repeated lack of progress still escalate to the
   owner.
6. SQLite, Web summaries, and other projections are rebuildable, but they do
   not replace EventLog, canonical stores, required artifacts, or evidence
   sidecars.
7. Feishu, Channel, and external controlled actions require additional
   credentials and routing. Credentials, action tokens, and provider secrets
   must not be committed.
8. This release primarily targets a trusted local development environment.
   Bind the Dashboard to `127.0.0.1` unless the network is explicitly trusted.
9. This release does not guarantee automatic migration from internal
   experimental tags or arbitrary historical runtime state. Archive the state
   directory, render the current configuration, and run cold-start validation
   and an isolated dry run before upgrading.

## Safety Boundaries

- `zf.yaml` is the only control-plane configuration. Do not hard-code or assume
  that the state directory is always `.zf/`.
- Agents may submit facts, artifacts, evidence, and intent. They may not
  directly mutate Kernel-managed truth.
- Mutations from Web, APIs, and integrations must use token-gated controlled
  actions.
- Bind the Dashboard to loopback unless the network is explicitly trusted.
- Never use `tmux kill-server` to stop one project; it can terminate unrelated
  sessions on the same host.
- Read the [Disclaimer](../../DISCLAIMER.md) before enabling external
  providers, Feishu, or unattended execution.

## Release and Compatibility

- `v0.0.1` is the first public release and the beginning of the public version
  line.
- The release tag must point to a specific commit that passed release
  validation.
- Before 1.0, ZaoFu aims to preserve compatibility where practical but may
  make necessary breaking changes.
- After changing a Controller or schema, render the configuration again, run
  cold-start validation, and execute an isolated mock E2E. Run the matching
  real-provider E2E before real delivery.

Before creating the `v0.0.1` tag, maintainers should run at least:

```bash
bash scripts/dev-premerge-gate.sh
uv run pytest -q --no-cov
npm --prefix web test
npm --prefix web run build
```

They should also complete a real-provider release drill with at least one PRD,
Issue, or Refactor Controller and inspect the plan, task map, Impl evidence,
Verify verdict, Thin Judge claim, delivery result, Goal Dossier,
restart/resume behavior, and final goal terminal state.

## Summary

ZaoFu v0.0.1 establishes a working multi-agent harness-engineering baseline.
Agents plan, implement, independently verify, and make semantic judgments. The
deterministic Kernel owns identity, state, evidence, recovery, delivery, and
side-effect boundaries. Operators can observe and take control through Web,
CLI, or Feishu.

This is the first public starting point, not a stable endpoint. v0.0.1 has the
complete product skeleton needed to experiment with real PRD, Issue, and
Refactor delivery while still requiring project-specific adaptation, real
quality gates, and a provider drill before release.
