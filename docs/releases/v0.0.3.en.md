## v0.0.3

v0.0.3 extends the Channel, PRD, Task, and controlled Workflow delivery path introduced in v0.0.2
to **Project-scoped Feishu collaboration groups**. The goal is not to turn Feishu into a second
control plane. Group messages, cards, approvals, runtime state, and long-text projections all remain
within the same EventWriter, controlled-action, and auditable-evidence boundaries.

```text
Project Feishu group
  -> exact (app_id, chat_id) route to a Project
  -> controlled Kanban Agent / Run Manager handling
  -> Channel / PRD / Task proposal
  -> Owner-approved Plan / Workflow action
  -> ZaoFu Event / Artifact / Delivery evidence
  -> Feishu progress and result projection
```

A message never directly creates a canonical Task, starts a Workflow, or mutates canonical state
outside the `events.jsonl` ledger. External effects continue to use controlled CLI actions, verified
callbacks, and the Kernel lifecycle.

## Highlights

### 1. Project Feishu Groups and a Multi-Workspace Bridge

- Each Project can explicitly manage one Feishu collaboration group. The binding is a project runtime
  sidecar; the Workspace holds only a rebuildable exact routing index.
- `auto_provision: false` remains the default. `zf init` only registers the Project and creates a
  `pending` binding; it does not create a real Feishu group implicitly.
- Only explicit `auto_provision: true` or
  `zf feishu group provision --confirm` / `attach --confirm` calls Feishu. Owner and configured bots
  must then be read back successfully; failures remain `repair_required`, never a fabricated `active`.
- One host/App WebSocket is shared through leases by Projects in multiple Workspaces. Inbound events
  select a Project through exact `(app_id, chat_id)` matching with no wildcard fallback.
- Real group members are the Owner, Kanban Agent App bot, and Run Manager App bot. Internal Codex,
  Claude Code, and OpenClaw Channel members are represented by those bots and are not impersonated as
  Feishu App members.

### 2. Feishu to Controlled Delivery

- An ordinary Project-group message reaches the `primary_responder`; an explicit mention of the
  Kanban Agent or Run Manager selects that target.
- The Kanban Agent can answer project status from a canonical projection without launching a Provider
  run, while preserving the same Channel message and completion-event lifecycle.
- Channel / PRD / Task and Workflow requests remain auditable proposals. Plan questions and approval
  cards reach Feishu, but only an Owner confirmation can admit a controlled action to
  `workflow.invoke.requested`.
- Catch-up cursors, idempotency, and Project bindings are separate per `(app_id, chat_id)`, preventing
  restart recovery from mixing messages, threads, or agent sessions across Projects.

### 3. Readable Replies and Reliable Stream Projection

- Reply, progress, question, delivery, and failure signals render as human-facing Feishu cards instead
  of raw internal event JSON.
- Inbound replay, async dispatch, stream completion, and final delivery cards converge through
  idempotent correlation, preventing duplicate completion cards for one Agent reply.
- Long PRDs, reviews, and scan results remain in ZaoFu Channel / artifact sidecars. Feishu cards carry
  concise summaries and actionable state; a chat card is not an unbounded evidence store.

### 4. Tighter Feishu / lark-cli Operations Contract

- Project-group operations use a restricted `lark-cli` argv. Secrets travel only through the
  environment, never binding files or command arguments.
- Creating groups, reading members, and adding members require `im:chat:create`,
  `im:chat.members:read`, `im:chat.members:write_only`, and `lark-cli >= 1.0.64`.
- Docx / Base Automation and Kanban sync remain one-way external publication surfaces. Feishu cannot
  write Tasks, Kanban state, or the EventLog back into ZaoFu.

## Delta from v0.0.2

From `dc6e79c0` to candidate commit `968a33fc`:

- 17 commits, 15 of them non-merge;
- 109 files changed: 11,970 additions and 436 deletions;
- the primary delta is Feishu Project-group binding, Workspace bridge leasing, inbound catch-up,
  Kanban Agent status replies, Plan/Delivery cards, and idempotent Channel stream convergence.

This is not another scheduler. The canonical owners for Tasks, Workflows, Runs, Channels, Artifacts,
and EventLog have not changed. Feishu can request or project controlled state only.

## Upgrade Notes

### 1. Finish Release Preparation

This draft does not perform the version bump. Before creating the formal `v0.0.3` tag, align package,
CLI, and Web version metadata to `0.0.3`, then reinstall dependencies from the final commit:

```bash
uv sync --extra dev --extra web --extra feishu
npm --prefix web ci
uv run zf --version
```

Expected after the formal release:

```text
zf 0.0.3
```

### 2. Enable a Project Feishu Collaboration Group

Start with the default no-external-write path and read back the binding:

```bash
uv run zf init --workspace default
uv run zf feishu group status
lark-cli --version
```

After confirming the Owner's app-scoped open ID, both bot credentials, permissions, and
`lark-cli >= 1.0.64`, use `auto_provision: true` or `zf feishu group provision --confirm`. Attach an
existing group through `zf feishu group attach --chat-id <chat_id> --confirm`; do not hand-write a
runtime `chat_id`.

### 3. Compatibility

- Projects that do not enable `feishu_project_group` continue to use `integrations.feishu_routing`.
- Do not start multiple debug bridges for the same App; managed sidecars use a host/App singleton lock.
- As a Developer Preview, Python APIs, Web APIs, event schemas, Controller profiles, and parts of the
  CLI may still change incompatibly before 1.0.

## Known Limitations and Release Blockers

1. **Real Feishu E2E is not yet release evidence:** Project-group / bridge behavior passed deterministic
   mock, integration, and post-merge regression tests. An operator with target-tenant permissions must
   still run isolated Workspace group creation, inbound, approval, and readback tests.
2. **Cross-App open IDs:** the Owner open ID must be visible to the provisioner App. Otherwise Feishu
   returns `open_id cross app` and the binding remains `repair_required`.
3. **Group membership model:** internal Coding Agents are not individual Feishu bots and cannot be
   mentioned directly. Collaborate through Channel roles represented by Kanban Agent or Run Manager.
4. **Long-text boundary:** Feishu cards do not automatically split into a long document. Audit bodies and
   large evidence remain in ZaoFu artifact sidecars / Channels.
5. **Formal release still needs validation:** after version alignment, rerun complete verification from
   the final candidate and perform at least one real Provider + Feishu release E2E without modifying
   ZaoFu source during the run.

## Summary

v0.0.3 promotes Feishu from a notification endpoint to a Project-scoped, readable, recoverable
collaboration surface while retaining the ZaoFu deterministic Kernel as the only control plane. Group
messages can advance discussion and controlled delivery, but cannot bypass Owner confirmation, action
tokens, the event ledger, or independent verification.
